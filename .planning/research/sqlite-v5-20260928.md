# Research sqlite-v5 — SQLite v4→v5 migration best practice (ManyProxy store)

**Decision this informs:** how to ship schema v5 (per-sub `interval_secs`, `health_history` + retention, `route_presets` extension) without stranding v4 databases, corrupting restores, or regressing batch/traffic paths.
**Confidence:** high on SQLite mechanics (sqlite.org docs); medium on rusqlite mapping (docs.rs 0.40); proposal sections marked where the repo must choose.
**Repo baseline (verified `src/store.rs`):** `SCHEMA_VERSION = 4`, `PRAGMA user_version` staged migration, `CREATE TABLE IF NOT EXISTS` + `ensure_column` (probe `pragma_table_info` → `ALTER TABLE ADD COLUMN`), STRICT tables (needs SQLite 3.37+, asserted via `MIN_SQLITE`), single-connection `rusqlite 0.40 bundled`, single-tx `add_batch` / `save_health_snapshots` / `restore_library_json`, loud fail on newer-than-supported version and on post-migration drift.

## TL;DR

1. Keep the existing staged `user_version` pattern: read version once → `CREATE TABLE IF NOT EXISTS` baseline → `ensure_column` backfills → version-gated data migrations → re-read/verify → bump `PRAGMA user_version = 5` last. Never bump before the data work commits.
2. v5 deltas are all ADD-COLUMN / CREATE-TABLE shaped (no 12-step rebuild): `subscriptions.interval_secs INTEGER NOT NULL DEFAULT 86400`, `health_history` append-only table, `route_presets` extension columns. All are online (`ALTER TABLE` time independent of row count for constraint-free adds).
3. Atomic restore = validate-then-rebuild inside one SQLite tx on a **temp DB file + fsync + atomic rename**, not `VACUUM INTO` (which copies/vacuums but does not validate or swap). `VACUUM INTO` is a backup primitive, not a restore primitive.
4. Batch traffic updates: one `Connection::transaction()` + prepared-statement loop + single `commit()`; validate-all-before-write or savepoint-per-row depending on the chosen row-error policy.
5. Corrupt-row quarantine: make list paths total (row-map returns `Result`, collector skips-and-counts with `PRAGMA integrity_check` / `quick_check` as the escalation, never fail-the-whole-list). Keep write paths strict.

## 1. Staged user_version migration (v4→v5)

- `PRAGMA user_version` is a free 32-bit integer in the DB header reserved for app versioning (sqlite.org `pragma.html#pragma_user_version`). Recommended pattern is exactly what `store.rs:create_schema` already does: branch on it at open, migrate forward idempotently, reject `version > SCHEMA_VERSION` loudly. Source: https://www.sqlite.org/pragma.html#pragma_user_version
- Stage order for v5 (extends current code, no redesign):
  1. `assert_sqlite_version()` first (STRICT + new DDL still needs ≥3.37).
  2. Read `PRAGMA user_version`; fail loudly if `> 5` (keep current message: open with newer build, never wipe).
  3. `CREATE TABLE IF NOT EXISTS` for every table (keeps `user_version = 0` legacy path working — fresh and v0 both converge).
  4. `ensure_column` backfills for all pre-v5 columns (existing loop) **plus** the three v5 deltas below.
  5. `if version < 5` data migration block (backfill `interval_secs`, create indexes, seed `route_presets` additions, optional `health_snapshots`→`health_history` seed). Idempotent: safe to re-run after a crash mid-migration because each step is `IF NOT EXISTS` / `column_exists`-guarded.
  6. Post-migration drift check (extend the existing `(table, column)` loop with the new columns); fail loudly with "restore from export" guidance.
  7. `PRAGMA user_version = 5` **only after** all of the above succeed. This is the crash-safety property: a kill mid-migration leaves the old version number, so next open re-runs the migration instead of trusting a half-migrated file.
- Why not one-shot DDL: `user_version` has no transactional coupling to DDL by itself; the safety comes from bumping it last. SQLite transactions are atomic (all-or-none per tx, durable after commit; see `atomiccommit.html`), but DDL batches across versions are clearest as separate staged blocks with the version bump as the commit marker. Source: https://www.sqlite.org/atomiccommit.html
- rusqlite mapping: `Connection::transaction()` rolls back on drop by default; `tx.commit()` is the explicit success path (`Transaction` docs). So each version-gated data block should be its own `transaction()` scope, and the final `PRAGMA user_version = 5` executes only after they commit. Source: https://docs.rs/rusqlite/latest/rusqlite/struct.Transaction.html

## 2. Adding columns (per-sub `interval_secs`)

- `ALTER TABLE … ADD COLUMN` appends the column; execution time is **independent of table size** when no new CHECK/UNIQUE/PK constraints force a table rewrite (sqlite.org `lang_altertable.html`, §4). A `NOT NULL DEFAULT 86400` integer add is the cheap case: existing rows fill with the default without a rewrite.
- Restrictions that matter for v5 (same source): no `PRIMARY KEY`/`UNIQUE` on added columns, no non-constant defaults, `NOT NULL` requires a non-NULL default. Proposed DDL fits:
  ```sql
  ALTER TABLE subscriptions ADD COLUMN interval_secs INTEGER NOT NULL DEFAULT 86400;
  ```
  Backfill policy: `NULL`/missing → `DEFAULT_AUTO_REFRESH_SECS` (86400, already `store.rs:981`); `<= 0` → treat as due (matches existing `due_for_refresh` semantics, `store.rs:994-1002`) rather than rejecting old rows.
- Keep using the repo's `ensure_column(table, column, ddl)` guard (probe `pragma_table_info`, add only if absent). It is the correct idempotency wrapper around the `ADD COLUMN` limits above.
- Do **not** use the 12-step table-rebuild procedure (§8 of the same page) for this delta — that is for PK/UNIQUE/reorder/type changes. `interval_secs` needs none of those. Source: https://www.sqlite.org/lang_altertable.html
- STRICT-table note: new columns inherit the table's STRICT typing; `INTEGER NOT NULL DEFAULT 86400` is STRICT-legal. Keep `MIN_SQLITE = (3,37,0)` assertion (STRICT arrived in 3.37).

## 3. New tables (`health_history` with retention, `route_presets` extension)

- `health_history` (new, append-only; proposal — names negotiable):
  ```sql
  CREATE TABLE IF NOT EXISTS health_history (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    config_id TEXT NOT NULL,
    at INTEGER NOT NULL,
    kind TEXT NOT NULL DEFAULT 'url-test',
    latency_ms INTEGER,
    error TEXT
  ) STRICT;
  CREATE INDEX IF NOT EXISTS idx_health_history_config_at
    ON health_history(config_id, at);
  ```
  Rationale: today's `health_snapshots(config_id PK, …)` keeps only the latest sample per config (`store.rs:411-425`); history needs a separate table so the latest-fast-path (`load_health_snapshots`) never pays a scan. Composite `(config_id, at)` index serves per-row charts + range deletes.
- Retention (proposal): delete by time, not by count — `DELETE FROM health_history WHERE at < ?` on a cadence (e.g. startup + daily, keep 30–90 days), **inside one tx**, followed by no `VACUUM` (see §4: WAL + freelist reuse is fine; `VACUUM` doubles disk footprint during the copy). Optionally cap with `DELETE … WHERE id NOT IN (SELECT id … ORDER BY at DESC LIMIT N)` per config if disk-bounded history is required; time-based is preferred (predictable size, no per-config skew).
- `route_presets` extension (proposal): additive only — new nullable columns via `ensure_column` (e.g. `description TEXT`, `is_builtin INTEGER NOT NULL DEFAULT 0`, `last_used_at INTEGER`), never rename/retype existing columns (would trigger the 12-step rebuild). Keep `name UNIQUE` + `idx_route_presets_name`; keep the no-FK rule (`preset_id` validated on attach, `store.rs:1537-1539`) so preset edits never cascade into `proxy_configs`.
- Fresh-DB vs migrate parity: because `create_schema` runs `CREATE TABLE IF NOT EXISTS` with the full v5 text on every open, fresh DBs and migrated v4 DBs converge to identical DDL — the drift-check loop then proves it.

## 4. Atomic restore (temp DB + rename vs VACUUM INTO)

- Recommendation: **temp DB file + fsync + atomic rename** (already the export pattern via `tmp_export_path`, `store.rs:1278-1291`). `VACUUM INTO` is the wrong tool for restore.
- What `VACUUM INTO` actually does (sqlite.org `lang_vacuum.html`, §2.1): creates a **new, minimal, fully-vacuumed copy** of the *source* DB at the target path; source unchanged; target must not exist (or must be empty); output is a consistent snapshot. It is listed alongside the backup API as a **backup** technique (`backup.html` §1.1: "Online Backup API … `VACUUM INTO` … `sqlite3_rsync`"), not a restore/swap technique. It does not validate payload semantics, does not remap DPAPI-sealed params, and performs a full copy+vacuum (CPU + up to ~2× disk during the copy per §3 "How VACUUM works"). Source: https://www.sqlite.org/lang_vacuum.html / https://www.sqlite.org/backup.html
- Restore pattern to keep/extend (matches current `restore_library_json` single-tx rebuild, `store.rs:3223-3285`):
  1. Validate the full payload **before** touching the live DB (current code already fails loudly on bad id/port/failures sections — keep that gate).
  2. Build into a **temp sibling DB in the same directory** (same filesystem → rename is atomic; also matches the existing `.tmp-<pid>` export helper).
  3. `fsync`/close, then atomic rename over the live path; never overwrite the live file in place, never `DELETE` + re-`INSERT` into the live file without the temp stage (a crash between wipe and rebuild loses the library).
  4. Keep `route_presets` out of the wipe (current ticket-37 ruling: presets survive restore for re-attach) — document explicitly since it surprises.
- Corruption angle: never `cp`/copy a live DB file while a tx may be active — the copy can mix old/new pages and is corrupt by construction; use the backup API or `VACUUM INTO` for *backups*, temp+rename for *restores* (sqlite.org `howtocorrupt.html` §§1.2–1.4). Source: https://www.sqlite.org/howtocorrupt.html
- Extra guard: run `PRAGMA quick_check` (fast subset of `integrity_check`) on the temp DB before rename; `integrity_check` returns `ok` or up to N error rows (sqlite.org `pragma.html#pragma_integrity_check`). Loud-fail the restore on any error row rather than swapping a corrupt file into place.

## 5. Batch traffic updates in one tx

- Current state (`store.rs:3293-3330`): `add_traffic(id, rx, tx)` does SELECT-then-UPDATE per call (two statements per row, autocommit each). Correct for single ticks, wasteful for poller sweeps (N rows → 2N round trips, N commits).
- Target pattern (proposal, rusqlite-idiomatic):
  ```rust
  let tx = conn.transaction()?;               // DEFERRED default; rolls back on drop
  let mut stmt = tx.prepare_cached(
    "UPDATE proxy_configs SET traffic_rx = traffic_rx + ?1, traffic_tx = traffic_tx + ?2 WHERE id = ?3")?;
  for (id, rx, tx_bytes) in deltas { stmt.execute(params![rx, tx_bytes, id])?; }
  drop(stmt); tx.commit()?;
  ```
  One transaction ⇒ one journal flush + one commit ⇒ all-or-none (sqlite.org `lang_transaction.html`: tx persists until COMMIT/ROLLBACK; `atomiccommit.html` for the durability mechanics). Sources: https://www.sqlite.org/lang_transaction.html / https://docs.rs/rusqlite/latest/rusqlite/struct.Transaction.html
- Semantics to preserve: saturating `i64::MAX` accumulation (SQLite ints are signed 64-bit — current `saturating_add` stays), unknown-id policy (today `NotFound`; batch must decide: fail-whole-batch vs skip-and-report — recommend skip-and-count to match §6 quarantine philosophy), probe exclusion (probe bytes never enter these counters — ticket-36 ruling).
- Transaction kind: default DEFERRED is fine (single writer, short tx). `IMMEDIATE` only if the poller contends with a concurrent writer and `SQLITE_BUSY` appears; `EXCLUSIVE` blocks readers — avoid. `busy_timeout` (already a connection PRAGMA in this app) covers transient locks. Source: https://www.sqlite.org/lang_transaction.html §2.2.
- Do not hold the tx across network I/O (Clash `/connections` poll); collect deltas first, then open/commit the tx. Long-held write txs escalate locks and force cache spills (extra fsyncs; `atomiccommit.html` §6.3).

## 6. Corrupt-row quarantine (tolerant list)

- Problem: strict row mappers (`map_row` fails loudly on out-of-range ports, `map_snapshot_row` clamps latency, DPAPI unseal fails loudly) mean **one bad row fails the whole list query** when using `query_map` + `collect::<Result<…>>`. For a library list UI that must always render, prefer quarantine over abort.
- Recommended shape (proposal):
  - Keep write paths and single-row reads strict (fail loudly — current behavior is right there).
  - Add a tolerant list collector: map each row to `Result<ProxyConfig, RowFault>`; partition into `(good, faults)`; return goods + a `faults: Vec<{id, column, cause}>` summary (counts + ids, never secret/param bytes). UI renders goods with a "N rows need attention (re-import or restore)" banner.
  - Precedent already in-repo: `decode_failures` returns `[]` on any corruption (never crash, never error — `store.rs:1040-1087`); `RoutePreset::rules()` fails per-preset with a re-import hint (`store.rs:571-579`). Extend that per-row philosophy to the config list.
- Detection/escalation: `PRAGMA integrity_check` (full, ≤100 errors default) / `quick_check` (faster, most checks) for page-level corruption; `PRAGMA foreign_key_check` for FK drift (no FKs in this schema today, so informational). These return result rows (`ok` vs error strings), so they compose with the quarantine report. Source: https://www.sqlite.org/pragma.html (integrity_check / quick_check / foreign_key_check sections).
- What NOT to do: `PRAGMA writable_schema=ON` + hand-editing `sqlite_schema` (supported but flagged corrupt-on-typo in `lang_altertable.html` §7–8); `PRAGMA ignore_check_constraints`; file-level copying of a live DB (§4). All trade short-term convenience for corruption risk.
