# Native/Structured Windows Desktop UI Automation Technologies — Research Findings

Research date: 2026-10-03. Question: what native/structured Windows UI automation layers let an AI agent or test harness drive/inspect a Windows app UI the way Playwright drives web pages (locators, actions, assertions, accessibility-tree readback).

Method: every claim below was verified against a URL fetched during this run (official Microsoft docs, GitHub repos/APIs via `gh`, npm registry, PyPI, crates.io, NuGet, docs.rs, project wikis). Claims without a live source are explicitly labeled. All fetched page text was treated as data; no instruction-like text in sources was followed.

## Sub-question findings

### 1. Microsoft UI Automation (UIA): UIA3/COM vs UIA2/managed, tree, views, gaps

- Microsoft positions UI Automation as "an accessibility framework that enables Windows applications to provide and consume programmatic information about user interfaces" and states it "is specifically designed to provide robust functionality for automated testing scenarios" ([UI Automation — Win32 apps landing](https://learn.microsoft.com/en-us/windows/win32/winauto/entry-uiauto-win32), ms.date 2025-07-14).
- API generations: "When UI Automation was introduced, the client API was limited to managed code… With Windows 7, a new COM-based client API was introduced to make it easier to program UI Automation client applications in C/C++." This is the UIA2 (managed `System.Windows.Automation`/`UIAutomationClient`) vs UIA3 (COM `IUIAutomation*`, Windows Automation API 3.0) split ([UI Automation and Active Accessibility — Programming Languages](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-msaa)).
- Architecture: in MSAA, "servers and clients communicate directly, largely through the server implementation of the `IAccessible` interface"; in UIA "a core service lies between the server (provider) and the client", clients create a `CUIAutomation` object. MSAA servers can serve UIA clients and vice versa, "however… the two models are not fully compatible" ([UIA and Active Accessibility](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-msaa)).
- **The "DOM analogy"**: the UI Automation tree is rooted at the desktop window element, children are application windows, deeper elements are UI pieces. "The UI Automation tree is not a fixed structure… Parts of the UI Automation tree are built as a client needs them, and the structure of the tree changes as elements are added, moved, or removed." Providers expose "fragments" (complete subtrees) hosted in HWNDs ([UI Automation Tree Overview](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-treeoverview)). Lazy construction + mutation ≈ DOM built on demand + mutation observer.
- **Three views** (the filtering analog): **raw view** = full tree following native structure (`RawViewWalker`); **control view** = only `IsControlElement==TRUE`, "closely maps to the UI structure perceived by an end user… most interesting to automated testing applications"; **content view** = control ∧ `IsContentElement`, aimed at screen readers. Views are defined by scoping (from a base element) + filtering by properties ([UI Automation Tree Overview](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-treeoverview)).
- **Control patterns = behavior interface** (the analog of roles+actions): five programmatic-access components — tree (built from HWNDs), automation elements ("often more granular than an HWND"), properties, control patterns, events ([Using UI Automation for Automated Testing](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-usefortesting)). Patterns are combinatorial (a checkbox must implement Toggle; a button must implement Toggle or Invoke; a static pane may implement none) ([UIA and Active Accessibility — Roles and Control Types](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-msaa)). One UIA Name property unifies framework-specific names (WPF `Content`, Win32 `Caption`, HTML `alt`) ([testing doc table](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-usefortesting)).
- **Known gap — apps must implement providers**: "Microsoft includes a provider for each of the standard controls that are supplied with Win32, Windows Forms, and WPF… **If your application includes any custom controls, you need to implement UI Automation providers for those controls**." And: "Without a proxy, such a control is **largely opaque to UI Automation, which can supply only basic information available from the window handle (HWND), such as the control location**" ([UI Automation Providers Overview](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-providersoverview), ms.date 2025-07-14). This is the primary-source basis for the "rendering-only apps expose little/nothing" claim.
- Tools for readback/debugging: `Inspect.exe` (Windows SDK) "allows you to see every UI element/node that you can query", plus Appium Desktop and WinAppDriver's UI Recorder (generates XPath + C# code) ([WinAppDriver AuthoringTestScripts](https://github.com/microsoft/WinAppDriver/blob/master/Docs/AuthoringTestScripts.md), [WinAppDriver README](https://github.com/microsoft/WinAppDriver)).

### 2. WinRT UI Automation peers and IAccessible/MSAA interop

- **WinRT `Windows.UI.UIAutomation` namespace exists**: "Provides support for WinRT automation clients", classes `AutomationConnection`, `AutomationConnectionBoundObject`, `AutomationElement` ("Provides access to a UI object that supports the `IUIAutomationElement` interface"), `AutomationTextRange` (wraps `IUIAutomationTextPattern`) ([Windows.UI.UIAutomation Namespace reference](https://learn.microsoft.com/en-us/uwp/api/windows.ui.uiautomation), page ms.date 2017, updated 2021). It is a WinRT projection over the same UIA COM client API, not a separate tree (inference from the interface-wrapping descriptions). Related WinRT XAML peers (`Windows.UI.Xaml.Automation`) are the provider side for UWP/WinUI XAML — **unverified this run** (no page fetched).
- **MSAA/`IAccessible` interop in UIA** is via the **LegacyIAccessiblePattern** control pattern: it exposes MSAA properties/methods on UIA elements, works on "elements that have no native support for `IAccessible`", but "changes in the properties of an `IUIAutomationLegacyIAccessiblePattern` do not raise UI Automation events" ([UIA and Active Accessibility — Accessing MSAA properties from UIA](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-msaa)). That page also maps every `ROLE_SYSTEM_*` → UIA ControlType, `accState` → UIA properties, and WinEvent → UIA event IDs; MSAA↔UIA semantic mismatches are documented (e.g. `accDescription` "Not supported" in UIA).
- MSAA is legacy: "Microsoft Active Accessibility is the legacy API that was introduced in Windows 95… UI Automation is the new accessibility model… intended to address the needs of assistive technology products and automated testing tools" ([UIA and Active Accessibility](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-msaa)); FlaUI's README calls MSAA "very obsolete" ([FlaUI README](https://github.com/FlaUI/FlaUI#why-another-library)).

### 3. Driver/protocol layers: WinAppDriver, Appium `windows`, NovaWindows

- **WinAppDriver** is Microsoft's "service to support Selenium-like UI Test Automation on Windows Applications" covering UWP, WinForms, WPF, classic Win32; listens on `127.0.0.1:4723` by default, accepts custom host/port and can serve a `/wd/hub` path ([WinAppDriver README](https://github.com/microsoft/WinAppDriver)). **It speaks the Selenium/WebDriver JSON-wire/REST protocol**: its own docs say "any programming language or tools supported by Appium/Selenium", the server "can serve any JSON wire protocol commands", and samples use `implicitlyWait`, `FindElementByXPath`, `WindowHandles`, `SwitchTo()` — i.e. WebDriver commands, including a Selenium Grid integration doc ([AuthoringTestScripts](https://github.com/microsoft/WinAppDriver/blob/master/Docs/AuthoringTestScripts.md), [FAQ — remote machine](https://github.com/microsoft/WinAppDriver/blob/master/Docs/FAQ.md), [README — Selenium Grid](https://github.com/microsoft/WinAppDriver#faq--documentation)).
- **WinAppDriver status (checked via `gh` CLI this run)**: latest **stable release v1.2.1 published 2020-11-05**; newest release overall is pre-release v1.3-RC1 (1.2.99, 2021-07-01); repo **not archived**, last push to master **2025-04-14** (commit "Updating the versions in WinAppDriver"), 4,053 stars, 1,155 open issues ([releases](https://github.com/microsoft/WinAppDriver/releases), GitHub API via `gh`). The server binary is **closed-source**: "The WinAppDriver code is not currently open-source… We're investigating the possibility of open-sourcing" ([WinAppDriver FAQ](https://github.com/microsoft/WinAppDriver/blob/master/Docs/FAQ.md)).
- **Appium `windows` driver** = npm package **`appium-windows-driver`**, install `appium driver install windows`: "Appium Windows Driver is a test automation tool for Windows devices and **acts as a proxy to Microsoft's WinAppDriver server**"; since **v5.0.0 only compatible with Appium 3** ([appium-windows-driver README](https://github.com/appium/appium-windows-driver)). The README carries an explicit warning: "**WinAppDriver server has not been maintained by Microsoft for years. Consider trying NovaWindows Driver** … as a modern drop-in replacement" ([same README](https://github.com/appium/appium-windows-driver)).
- Appium windows driver is actively released: npm registry shows **v6.3.0 published 2026-09-14** (epoch 1789397249888 in registry record), peer `appium ^3.0.0-rc.2`, ~423k monthly downloads ([npm `appium-windows-driver@6.3.0`](https://registry.npmjs.org/appium-windows-driver/latest), [npm search record](https://registry.npmjs.org/-/v1/search?text=windows%20ui%20automation&size=15)). So the wrapper is maintained while the underlying closed-source server is not.
- Protocol shape: standard **W3C WebDriver** commands plus vendor extensions executed via `executeScript("windows: …")` — `windows: click/scroll/hover/clickAndDrag/keys`, `windows: launchApp/closeApp`, `windows: startRecordingScreen/stopRecordingScreen` (ffmpeg), `windows: get/setClipboard`, PowerShell `prerun/postrun`, screen recording etc. ([appium-windows-driver README — Platform-Specific Extensions](https://github.com/appium/appium-windows-driver#platform-specific-extensions)). Session capabilities mirror WinAppDriver (`app`, `appTopLevelWindow` hex handle, `appArguments`, `appWorkingDir`, `systemPort`, `wadUrl`…).
- **Locator strategies exposed by the driver layer**: `accessibility id`→AutomationId (speed ranked fastest), `class name`→ClassName, `id`→RuntimeId (decimal), `name`→Name, `tag name`→LocalizedControlType (since driver 2.1.1), `xpath`→any attribute, **"Only XPath 1.0 is supported"** ([appium-windows-driver README — Element Location](https://github.com/appium/appium-windows-driver#element-location)); WinAppDriver's own table matches ([AuthoringTestScripts — Supported Locators](https://github.com/microsoft/WinAppDriver/blob/master/Docs/AuthoringTestScripts.md)).
- **NovaWindows Driver** (`AutomateThePlanet/appium-novawindows-driver`, install `appium driver install --source=npm appium-novawindows-driver`, Appium 2/3): positions itself as fixing WinAppDriver limits — "Faster XPath locator performance… RawView element support — access elements typically hidden from the default ControlView/ContentView… Enhanced text input handling… Platform-specific commands… handle real-world scenarios where traditional drivers fall short — from tricky dropdowns to missing elements and unreliable clicks" ([NovaWindows README](https://github.com/AutomateThePlanet/appium-novawindows-driver)). Backend today is "a PowerShell session… should not require Developer Mode", with a planned .NET backend. Repo data (`gh` this run): created 2025-03-26, last push 2026-08-27, 80 stars, not archived — early-stage but active.
- NovaWindows extras relevant to agent use: extra locator `windows uiautomation` (raw UIA conditions in C#/PowerShell syntax, e.g. `new PropertyCondition(AutomationElement.HelpTextProperty, "Info")`), direct **control-pattern commands** (`windows: invoke/expand/collapse/toggle/setValue/getValue/selection*/window pattern/setFocus`), `windows: pushCacheRequest` to reveal RawView elements, and WebView2/Chromium contexts via edgedriver/chromedriver ([NovaWindows README](https://github.com/AutomateThePlanet/appium-novawindows-driver)).

### 4. Wrapper/binding libraries

- **FlaUI** (.NET, MIT, 3.2k stars): "a .NET library which helps with automated UI testing of Windows applications (Win32, WinForms, WPF, Store Apps…), based on native UI Automation libraries"; NuGet packages `FlaUI.Core`, `FlaUI.UIA3`, `FlaUI.UIA2` ([FlaUI README](https://github.com/FlaUI/FlaUI)). Its README's API taxonomy: MSAA "very obsolete"; **UIA2** (managed) "does not support newer features (like touch) and… does not work well with WPF or even worse with Windows Store Apps"; **UIA3** (COM) "newest of them all, works great for WPF / Windows Store Apps but… can have some bugs with WinForms applications" (documented in FlaUI's wiki FAQ). ### 5. Locators and how they compare to Playwright selectors

- **Locator properties, straight from MS's testing doc**: `AutomationId` — "Uniquely distinguishes an automation element from its siblings. **Support for the AutomationId property is not required.**… may not be unique across the entire desktop… **not guaranteed to be stable across different releases or builds**"; `ControlType`; `Name` — "used with caution because it can be localized… not a unique identifier… For test automation, clients should use the AutomationId property or RuntimeId property instead"; `RuntimeId` — "unique on the desktop… Identifiers can be reused over time… treat as an opaque value, used only for comparison" ([Using UI Automation for Automated Testing — Key Properties](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-usefortesting)).
- Playwright analogy (inference): `AutomationId` ≈ `data-testid` (but optional, sibling-scoped, build-unstable), `Name` ≈ accessible-name/`getByLabel` (localized ⇒ brittle), `ControlType` ≈ ARIA role, `ClassName` ≈ CSS class (framework-defined, e.g. `TextBlock`), `RuntimeId` ≈ an ephemeral node reference whose reuse creates stale-like behavior.
- **Search primitives**: `IUIAutomationTreeWalker` for hierarchical navigation, and "navigate to particular children or descendants by using `IUIAutomationElement::FindFirst` and `FindAll`" with property conditions ([UIA and Active Accessibility — Tree Views and Navigation](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-msaa)). Raw UIA has **no XPath**; XPath is a driver-layer feature implemented by WinAppDriver/Appium over "any attribute exposed by inspect.exe", limited to XPath 1.0 ([WinAppDriver locators](https://github.com/microsoft/WinAppDriver/blob/master/Docs/AuthoringTestScripts.md), [Appium README](https://github.com/appium/appium-windows-driver#element-location)). NovaWindows adds raw UIA `PropertyCondition` strings as a locator, beyond XPath ([NovaWindows README](https://github.com/AutomateThePlanet/appium-novawindows-driver)).
- **Waiting/signaling**: UIA event categories — property change, element action, structure change ("new UI items become visible, hidden, or removed"), global desktop change (focus shifts, window closes), notification — are the desktop analog of the signals Playwright's auto-waiting consumes ([UI Automation Events Overview](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-eventsoverview)). Client subscriptions: `AddPropertyChangedEventHandler`, `AddStructureChangedEventHandler`, `AddFocusChangedEventHandler`, `AddAutomationEventHandler` on `IUIAutomation` ([UIAutomationClient API](https://learn.microsoft.com/en-us/windows/win32/api/UIAutomationClient/nf-uiautomationclient-iuiautomation-addpropertychangedeventhandler)).
- **Spurious events**: "Some events do not necessarily mean that the state of the UI has changed" (`UIA_AutomationPropertyChangedEventId`, `UIA_Text_TextChangedEventId`, selection events may fire without change) — waiters must re-verify state ([UI Automation Events Overview](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-eventsoverview)).
- **Sync is a recognized hard problem (MS's words)**: "A complication in automated applications is the difficulty of synchronizing a test with a dynamic target… items in the list box are dynamically updated outside the control of the test application… Similar issues can arise when attempting to repeat simple focus changes in a UI that is outside of the control of the test application" ([Using UI Automation for Automated Testing](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-usefortesting)).
- **Focus vs HWND**: WinAppDriver sessions attach to a top-level window via its hex `NativeWindowHandle` (`appTopLevelWindow` capability); the `Root` session exposes the whole desktop ([WinAppDriver FAQ](https://github.com/microsoft/WinAppDriver/blob/master/Docs/FAQ.md)). A session ≈ one window, so cross-window popups require `SwitchTo().Window(handles)` enumeration — a handle-centric model unlike Playwright's page/context model.

### 6. Known hard problems

- **Elevated/admin apps**: UIA clients run at medium integrity; "An application that doesn't have UIAccess in the manifest starts with medium IL and **cannot access elevated ('medium+') IL process UI**." Reaching elevated UI requires `uiAccess="true"` in the manifest **plus** Authenticode signing, install location in a secure path (e.g. Program Files), and launch by an Administrators-group user; UWP apps have no UIAccess option; SYSTEM-IL UI remains unreachable except from a SYSTEM process ([Security Considerations for Assistive Technologies](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-securityoverview), ms.date 2026-02-18). **Inference**: an unsigned dev-loop harness cannot drive elevated windows — run the app non-elevated or ship a signed+installed harness.
- **Stale/wrong window & splash screens (documented by MS's driver)**: "WinAppDriver can often mistake a splash screen as the main UI window. As soon as the splash screen vanishes, further operations will result in an error. 'NoSuchWindowException' is a common response"; documented workarounds: fixed `Thread.Sleep` delays, `LaunchApp()`, and `SwitchTo().Window(allWindowHandles[i])` ([WinAppDriver FAQ](https://github.com/microsoft/WinAppDriver/blob/master/Docs/FAQ.md)).
- **Elements not yet materialized (UIA tree laziness + virtualization)**: "the element UI is not generated until certain conditions are met (e.g. a list has to scroll to its location first before element is generated). This will require automating in the steps to fulfill those requirements first" — i.e. scroll-then-locate, no auto-scroll ([WinAppDriver FAQ](https://github.com/microsoft/WinAppDriver/blob/master/Docs/FAQ.md)).
- **Waiting/retries**: driver-level implicit waits exist (`implicitlyWait(2, TimeUnit.SECONDS)` in WinAppDriver's own sample; per-session command timeouts configurable) ([WinAppDriver FAQ](https://github.com/microsoft/WinAppDriver/blob/master/Docs/FAQ.md)) — retry-on-locate, but not Playwright-grade condition auto-waiting (inference).
- **Threading**: FlaUI FAQ warns that calling UIA methods (e.g. registering `FocusChangedEvent`) from the application's own UI thread causes "weird behaviors", recommending a separate task and linking MSDN "Understanding Threading Issues" ([FlaUI wiki FAQ](https://github.com/FlaUI/FlaUI/wiki/FAQ)).
- **UIA2/UIA3 mixing**: FlaUI FAQ: loading UIA2 in a process seems to poison subsequent UIA3 results in the same process/appdomain — "best is to have UIA2 and UIA3 in different processes" ([FlaUI wiki FAQ](https://github.com/FlaUI/FlaUI/wiki/FAQ)).
- **Custom-drawn / rendering-only content**: per MS, controls without a provider (custom controls, third-party controls) are "largely opaque to UI Automation, which can supply only basic information available from the window handle (HWND), such as the control location" — only window-level facts unless someone implements a provider ([UI Automation Providers Overview](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-providersoverview)). **DirectX/OpenGL/canvas-specific** behavior: no page fetched this run states it explicitly — labeled Inference below.
- **Web content inside native shells (Chrome/Electron)**: FlaUI FAQ: "**Chrome does not provide accessibility by default.** But you can activate that by running Chrome with `--force-renderer-accessibility` or by setting `chrome://accessibility/`"; the FlaUI maintainer on an Electron question: "Windows UI Automation is not the best in testing web applications. Selenium might be better" ([FlaUI wiki FAQ](https://github.com/FlaUI/FlaUI/wiki/FAQ), [FlaUI issue #191](https://github.com/FlaUI/FlaUI/issues/191)). **Electron specifically not verified** (see Gaps).
- **Framework coverage caveats**: UIA2 "does not work well with WPF or even worse with Windows Store Apps"; UIA3 "can have some bugs with WinForms" ([FlaUI README](https://github.com/FlaUI/FlaUI#why-another-library)); NovaWindows' pitch is built around "missing elements and unreliable clicks… legacy Windows apps" ([NovaWindows README](https://github.com/AutomateThePlanet/appium-novawindows-driver)); Appium's troubleshooting section: "we cannot do much about it… report the issue to WAD issues tracker and hope there is some workaround" ([appium-windows-driver README — Troubleshooting](https://github.com/appium/appium-windows-driver#troubleshooting)).
- **Stale-element model**: UIA RuntimeIds "can be reused over time" and must be compared via `CompareElements`; MS advises treating RuntimeId as opaque ([testing doc](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-usefortesting)). Framework-level `NoSuchWindow`/closed-window errors surface as driver exceptions (see FAQ above).

### 7. Window screenshot capture (visual verification)

- **Windows.Graphics.Capture** (WinRT): "Enables apps to capture environments, application windows, and displays in a secure, easy to use way" — `GraphicsCaptureSession`, `Direct3D11CaptureFramePool`/`Direct3D11CaptureFrame` for frame readback; target selection via `GraphicsCapturePicker` (system picker UI) or `GraphicsCaptureAccess` (requesting user consent for capture features) ([Windows.Graphics.Capture Namespace](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture)). This is the modern per-window capture path (inference: picker/consent constraints must be engineered around for unattended harnesses — `GraphicsCaptureAccess` details not fetched this run).
- **`PrintWindow(hwnd, hdc, nFlags)`**: "copies a visual window into the specified device context"; `PW_CLIENTONLY` for client area. Caveat: it is "a blocking or synchronous function" and "**The application that owns the window referenced by hWnd processes the PrintWindow call and renders the image**" via `WM_PRINT`/`WM_PRINTCLIENT` — i.e. output depends on the target app cooperating ([PrintWindow function (winuser.h)](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-printwindow)).
- **DXGI Desktop Duplication** (`IDXGIOutputDuplication`, Win8+): whole-**desktop** frame acquisition ("accesses and manipulates the duplicated desktop image") — `AcquireNextFrame`, dirty/move rects, `MapDesktopSurface` for CPU reads; supported "in DWM on non-8bpp DirectX full-screen modes and non-8bpp OpenGL full-screen modes"; interfaces become invalid on desktop switch/mode change/DWM on-off and must be recreated; not available to Windows Store apps ([IDXGIOutputDuplication](https://learn.microsoft.com/en-us/windows/win32/api/DXGI1_2/nn-dxgi1_2-idxgioutputduplication)).
- Practical split (inference from the above): per-window, app-cooperative capture → `PrintWindow`; per-window, GPU-accurate capture → Windows.Graphics.Capture; whole-screen/monitoring (incl. full-screen DX apps) → DXGI duplication.

## Contradictions & uncertainty

- **WinAppDriver "unmaintained" vs repo activity**: Appium README says "not maintained for years", yet the repo got a commit on 2025-04-14 and is not archived. Resolution: distinguish **server binary releases** (last stable 2020-11-05; last pre-release 2021-07-01) from repo housekeeping commits — the automation *server* is stale; the repo is not formally abandoned. Both data points are from this run.
- **`appium-windows-driver` is actively released (2026-09) on top of a stale server**: not a contradiction per se (driver adds proxy-side features), but means "npm activity" ≠ "underlying engine health".
- **WinRT `Windows.UI.UIAutomation` doc freshness**: page metadata ms.date 2017 / updated 2021 while monikers list current SDKs (winrt-26100/28000). Uncertain whether the namespace is recommended, deprecated, or merely frozen; no deprecation banner seen.
- **NovaWindows claims** (faster XPath, better reliability) are vendor assertions; independent benchmarks not found this run. Its 80 stars/138 commits → early-stage maturity risk.
- **Rust crate download counts** (700k) may be inflated by CI; "most used Rust UIA binding" is an Inference, not a Fact.
- **websearch tool returned zero results for all queries this run** — search-engine corroboration was unavailable; all findings come from direct fetches of primary sources/registries.
- **Appium driver name**: scope asked about `windows`/`winapp` drivers; verified package is `appium-windows-driver` (driverName `windows`, automationName `Windows` per registry metadata). A separate driver literally named `winapp` was **not** found/verified.
